# EngineerWorkBoat Skills 说明书

> 版本：v1.1.0（单入口 Router 模式） · 更新日期：2026-11-22
> 设计参考：DeepSeek dsh-superagent-prototype（000 哲学 / 002 授权 / 003 执行）

---

## 1. 这套东西是什么

EngineerWorkBoat Skills 是一组**可复用的工作流 Skills**，用于把一个软件想法，从模糊需求一路推到经过独立验收的交付结果。

它不是一个常驻后台的"Super-agent 运行时"，而是一套**约定 + 阶段能力**：你只需和唯一的入口对话，其余的分工、调度、模型选择、结果核对都由这个入口在内部完成。

### 1.1 核心承诺（也是设计原则）

| 原则 | 含义 |
|---|---|
| 注意力最小化 | 只在"必须决策 / 无法继续 / 结果可用"时开口，其余时间保持静默 |
| 协调与执行分离 | 协调留在 Router，具体执行放进隔离的 Worker |
| 授权即输入 | 消息、引用、工具输出是输入，不能让授权悄悄变大 |
| 证据驱动完成 | 没有可回看的证据，不宣称完成 |
| 状态可恢复 | 依赖文件和交接记录，而不是靠聊天历史续命 |

### 1.2 一句话工作方式

> **你只跟 `dev-flow-router` 说话。它在合适的时机自动创建子会话干活、挑模型、回收结果、推进阶段，最后回到同一个会话给你结论。**

## 2. 唯一入口：dev-flow-router

### 2.1 它是什么角色

`dev-flow-router`（下文简称 Router）是整套 Skills 的**唯一用户入口**。你不需要打开、切换或管理多个会话，也不需要手动调用任何阶段 Skill。

Router 负责四件事：

1. **建立最小任务授权**：目标、范围、权限、验收、当前版本。
2. **按阶段分流**：判断当前缺口，决定该走哪个阶段 Skill。
3. **按需创建子会话并选模型**：确有收益才开 Worker，并为每个 Worker 指定模型。
4. **回收结果、核对证据、统一汇报**：Worker 的"完成声明"不直接等于验收通过。

### 2.2 最小任务授权（六要素）

Router 在接任务时先锁定六件事，任何消息、引用文档、工具输出都**不能**扩大这些边界：

| 字段 | 含义 |
|---|---|
| `outcome` | 用户最终能获得的可观察结果 |
| `scope` | 允许修改的模块、文件或系统 |
| `non_goals` | 明确不在本轮处理的事项 |
| `permissions` | 只读 / 本地写入 / 外部写入 / 发布，分别是否获准 |
| `acceptance` | 验收标准来源与必须执行的检查 |
| `version` | 分支、提交、构建号或可识别文件集合 |

一旦发现超范围工作，交回 Router 判断；需要业务决策时**停下来问**，而不是用更多执行来替代决策。

### 2.3 阶段分流表

| 当前缺口 | 阶段 Skill | 阶段产物 |
|---|---|---|
| 不知道资料在哪、跨会话无法恢复 | `repository-knowledge` | 简短仓库入口与资料索引 |
| 目标、首版范围或完成标准不清 | `product-spec` | 产品规格与可观察验收条件 |
| 页面布局和主要操作尚未验证 | `interactive-prototype` | 可点击原型与实测记录 |
| 架构、数据或依赖选择不清 | `technical-design` | 技术方案、取舍与风险 |
| 已具备明确实现范围 | `incremental-implementation` | 小步代码改动、自验结果与功能清单 |
| 需要独立核对用户可见结果 | `evidence-verification` | 通过 / 失败 / 受阻及证据 |
| 需要独立检查代码缺陷与遗漏 | `independent-code-review` | 可定位、可复现的 Review 结论 |
| 会话结束、中断或换人继续 | `development-handoff` | 可恢复状态与下一步 |

> 这八个阶段 Skill 是 Router 的**内部能力**，不是让你逐个开启的入口。单阶段任务也由 Router 承接。

## 3. 子会话与模型路由（本版本重点）

### 3.1 何时创建子会话

只有存在**明确收益**时才创建：

- 某阶段需要独立或更专业的上下文（规格、设计、实现）。
- 实现完成后，需要**未参与实现**的独立 Review 或最终验收。
- 两项工作相互独立、写入范围不重叠，可真正并行。
- 大范围只读调查会挤占 Router 的全局上下文。

**反例**：不要为九个 Skill 各开一个会话，也不要为一次小改动搭完整流水线。琐碎工作 Router 直接在主会话完成。

### 3.2 如何创建子会话

Router 通过环境提供的 `Agent` 工具创建临时子会话，每次调用明确指定：

| 参数 | 约定 |
|---|---|
| `subagent_type` | 只读调查用 `Explore`；产出/修改用 `general-purpose` 或更匹配的专用类型 |
| `name` / `description` | 按阶段命名，便于 Router 跟踪 |
| `model` | 用户显式指定优先；否则按任务选 `lite` / `default` / `reasoning` |
| `prompt` | 自包含：授权、绝对路径、应加载的 Skill、验收标准、已有决定、禁止动作、返回格式 |
| `run_in_background` | 仅当无需等待其结果即可推进其他工作时才设为 `true` |

### 3.3 默认模型策略

| 任务类型 | 默认模型 |
|---|---|
| 仓库搜索、资料定位 | `lite` |
| 一般实现、原型 | `default` |
| 产品取舍、技术设计、独立 Review | `reasoning` |

这是**默认路由**，不覆盖你的显式指定。Router 不编造不存在的模型 ID，也不为凑模型数量多开 Worker。

### 3.4 结果回收

- Worker 只向 Router 返回结果或待决策问题，**不直接向你提问或交付**。
- Router 核对实际文件、命令输出、证据后，决定推进、修复、复测或问你。
- 需要人工决策时，Worker 把问题交回 Router，Router 在当前会话**一次只问一个具体问题**。
- 子会话失败，Router 诊断后重派或本地接续，**不让你另开会话重述背景**。
- 环境没有 `Agent` 能力时，Router 本地降级执行并说明限制，不把多会话操作转嫁给你。

### 3.5 并行与上下文控制

- Router 始终保留全局状态和最终汇总责任，不创建嵌套 Router。
- 只并行"相互独立、写入不重叠、验收可区分"的工作。
- 独立 Review 和最终验收尽量用**新子会话**，不把实现者结论当证据。
- 耗时测试/构建/服务转成可追踪的后台工作。
- 恢复或重试前先查目录、版本、历史和既有外部结果，避免重复提交/推送/发布。

## 4. 状态契约与阶段门

### 4.1 状态：描述"正在等待什么"

| 状态 | 含义 | 退出条件 |
|---|---|---|
| `queued` | 已接收，等待执行资源 | Worker 开始执行 |
| `working` | 正在执行或有后台工作 | 结果 / 问题 / 失败 / 等待事件 |
| `awaiting-answer` | 需要人工决策 | 收到答案 |
| `awaiting-review` | 结果可审查，等待验收 | 通过或反馈 |
| `blocked` | 环境 / 权限 / 依赖阻断 | 阻塞解除 |
| `failed` | 已执行但失败 | 修复 / 重试 / 人工接管 |
| `ready` | 授权范围内已有可交付结果 | 新需求或关闭任务 |

> 状态是"等什么"，不是百分比。`ready` 必须附带**实际证据**和**未验证项**。

### 4.2 阶段门：有证据才推进

1. **规格门**：范围、非目标、核心流程已确认，验收条件可失败。
2. **设计门**：关键取舍、依赖、失败路径、验证策略已记录。
3. **实现门**：每个声称完成的小项都有实际检查结果，未验证项保持未通过。
4. **交付门**：独立验收与 Review 已完成；失败项已修复并用原步骤复测。
5. **外部动作门**：提交、推送、发布、发消息等仅按明确授权执行。

## 5. 八个阶段 Skill 速查

| Skill | 阶段 | 一句话职责 | 何时触发 |
|---|---|---|---|
| `repository-knowledge` | 启动 | 建立/修复仓库知识入口（AGENTS.md 等）与资料索引 | 新仓库、找不到项目规则、知识重复或过期 |
| `product-spec` | 产品 | 把模糊想法变成聚焦结果的规格、首版范围与可失败验收条件 | 需求或完成标准不清、改动扩大范围 |
| `interactive-prototype` | 原型 | 用示例数据做可点击原型并实测核心流程 | 页面结构与主要操作未验证 |
| `technical-design` | 设计 | 产出可落地但不冗余的技术方案（架构/数据/信任边界/依赖/失败处理） | 非平凡实现前、需求与架构冲突 |
| `incremental-implementation` | 实现 | 用功能清单小步实现，逐项自验并回填证据 | 功能开发、修 bug、长任务、中断续作 |
| `evidence-verification` | 验收 | 独立执行真实路径，返回 passed / failed / blocked 及证据 | 验收测试、回归、UI/API 校验、复测修复 |
| `independent-code-review` | Review | 全新只读上下文里审查代码，按严重度给出可定位结论 | 合并前 Review、实现后独立复查、回归风险 |
| `development-handoff` | 连续性 | 把可恢复状态与下一步持久化，供下一次会话续作 | 关键节点、上下文重置、失败/中断后 |

## 6. 最佳实践（6 个）

### 实践 1：只跟 Router 对话，别手动开多个会话

**做法**：把需求、参考文档、约束都发给 `dev-flow-router` 这一个入口；需要指定模型时，用一句自然语言说清楚（如"实现用 `default`，设计用 `reasoning`"）。

**为什么**：Router 持有全局目标和授权，由它统一调度才能保证上下文隔离、证据链连续、不重复劳动。

**反模式**：为 `product-spec`、`technical-design`、`incremental-implementation` 分别开一个会话来回传话——这正是本版本要消除的痛点。

---

### 实践 2：先让 Router 锁授权，再谈执行

**做法**：接任务时先和 Router 确认六要素（目标 / 范围 / 非目标 / 权限 / 验收 / 版本），尤其把"允许改什么、禁止改什么、能不能发布"说清楚。

**为什么**：授权一旦锁定，后续消息和工具输出都不能悄悄扩大它；超范围请求会被挡回 Router 而不是被默默执行。

**反模式**：先说"随便做"，等实现到一半又追加账号、支付、后台等新范围——这正是 product-spec 里"不自行增加功能"要防的。

---

### 实践 3：把"完成"定义成可失败、可复现的验收条件

**做法**：在规格阶段就为每个核心流程写清前置条件、真实入口、操作、预期结果、证据、失败情况，避免"体验良好""支持保存"这类不可判定措辞。

**为什么**：实现门和交付门都靠证据推进；验收条件能失败，才谈得上"通过"。

**反模式**：用"构建通过"或"代码写完了"当作功能验收，跳过真实用户路径。

---

### 实践 4：让验收和 Review 用"没碰过实现的新上下文"

**做法**：实现完成后，由 Router 用新的子会话执行 `evidence-verification` 和 `independent-code-review`，Review 拿到的是原始验收标准 + 实际差异，而不是实现者的自评摘要。

**为什么**：实现者"我测过了"不等于证据；独立上下文才能发现遗漏、回归和验证缺口。

**反模式**：让写代码的同一个会话"顺带验收一下"，把自我确认当成交付门证据。

---

### 实践 5：每一步都留交接，中断也不怕

**做法**：在每个关键节点用 `development-handoff` 记录当前版本、已改动文件、实际命令与证据位置、未验证项、阻塞点和唯一下一步。

**为什么**：状态从文件和交接记录恢复，而不是靠聊天历史；换会话、换人、上下文重置后能无缝续作。

**反模式**：把"已写代码"写成"已验收"，把推测结果写成事实，交接里塞满无关聊天。

---

### 实践 6：控制噪声，只在四个时点说话

**做法**：Router 只在"接收后确认一次、需要决策、无法完成、结果可用"四个时点输出；一次只问一个具体问题。

**为什么**：每个消息都在消耗你的注意力；能自己查到的答案不问，健康状态不制造额外通知。

**反模式**：执行中频繁发流水账，或一次抛五个问题让人挑——这违背"注意力最小化"的核心原则。

## 7. 快速上手示例

**场景：从想法到可验收交付**

1. 你只对 Router 说："我想做一个 X，核心流程是……，先出规格。"
2. Router 锁定授权 → 内部跑 `product-spec` → 回你确认范围 + 验收条件（`awaiting-answer`）。
3. 你确认 → Router 跑 `interactive-prototype` / `technical-design`（按需，可能并行）。
4. 方案确定 → Router 跑 `incremental-implementation`，逐项自验。
5. 实现完成 → Router 用新子会话跑 `evidence-verification` + `independent-code-review`。
6. 失败项修复复测通过 → Router 汇总改动、证据、未验证项，`ready`。

全程你只在一个会话里做三件事：**提需求、拍关键决策、验收结果**。

## 8. 边界与定位说明

- 本套件是**可复用的工作流 Skills**，不是常驻 Super-agent 运行时。
- 仅安装部分阶段 Skill 时，Router 按阶段目标降级执行，不因缺某个 Skill 停工。
- DeepSeek dsh-superagent 的 Slot 并发槽位、准入表（Admission）、Policy 版本、自动重试次数等**运行时机制**，这里用"仅并行不重叠工作""外部动作需明确授权"等轻量规则等价表达，未逐字照搬。
- 参考链接见 `skill-suite.json` 的 `sources` 字段。
