# 功能地图与证据规则

## 功能地图

为每个主要用户功能维护一条地图，至少包含：

1. 功能与子功能。
2. 前置条件、测试数据和隔离要求。
3. 从用户视角到达功能的真实入口。
4. 使用项目已有工具执行的操作步骤和稳定定位方式。
5. 可观察最终状态与必要副作用。
6. 已知限制、历史故障和不能自动判断的项目。

入口变化时更新地图。不要因为当前工具只能走一条方便路径，就删除其他需要覆盖的入口。

## 启动、诊断与清理

- 使用仓库已有启动方式，记录如何确认实例真正可用，而不只是端口可访问。
- 执行只读诊断，确认版本、实例归属、认证和依赖是否满足。
- 多实例无法隔离时明确说明，避免同时驱动共享会话或数据。
- 只终止本轮启动的进程，只删除本轮临时状态；证据必须保留。

## 证据强度

从强到弱优先选择：可重跑的自动断言、带版本的测试输出、操作前后截图或响应、持久化记录、人工观察。代码存在和构建成功只能支持对应结论，不能证明用户流程通过。

证据需能对应具体用例和版本。文件路径应相对报告位置保存并可打开；命令证据记录实际命令与关键输出；URL 证据记录具体位置而非站点首页。

## 失败与复测

先保存失败证据和最小复现，再交回实现。修复后保持输入、步骤和预期不变进行复测，追加新一轮结果；同时运行相关回归，不用新步骤掩盖旧失败。
